# Этапы 3–4: карантин legacy sync_outbox

Основание: [выбор протокола sync](sync_protocol_selection.md). Контракт v1:
любая историческая операция с отсутствующим `protocol_version`, значением `NULL`
или `0` имеет эффективное состояние `quarantined_legacy`. Все существующие
187 pending-операций должны игнорироваться v1 бессрочно, пока не выполнен отдельно
проверенный план ручной миграции. Возраст операции, повторная попытка, перезапуск,
валидный владелец и появление mapping не снимают карантин.

`quarantined_legacy` — решение отчёта, а не запись в `sync_outbox.status`.
Аудит не меняет `status`, payload, `protocol_version`, владельцев, mappings или
схему. Он не запускает приложение, migrations, sync worker или HTTP-запросы.
Фильтрация отправки v1 — отдельная обязанность worker: выбирать только явно
созданные операции версии 1. Этот инструмент не изменяет worker и не доказывает
его поведение во время работы приложения.

## Запуск только для чтения

Из `/Users/vjachikslavny/OVC`:

```sh
.venv/bin/python -B scripts/audit_legacy_sync.py --database /Users/vjachikslavny/OVC/src/ovc.db
```

По умолчанию JSON в stdout содержит **все** подходящие строки без лимита,
упорядоченные по ID, и сводку. Только сводка:

```sh
.venv/bin/python -B scripts/audit_legacy_sync.py --database /Users/vjachikslavny/OVC/src/ovc.db --summary-only
```

Без `--database` путь определяется существующим `scripts/local_data.py`
через config helpers. Явный путь позволяет обойти загрузку config и `.env`.
SQLite открывается существующим helper с URI `mode=ro`; дополнительно включён
`PRAGMA query_only=ON`. Один `BEGIN` удерживает согласованный снимок схемы,
очереди, пользователей, сущностей и mappings. Соединение закрывается по завершении.
`immutable=1` не используется: зафиксированные изменения WAL также учитываются.
Несуществующий файл не создаётся. Команда не пишет отчёт на диск и отключает
создание Python bytecode для импортируемых модулей.

Отбор: `status='pending'` и `protocol_version IS NULL OR protocol_version=0`.
Если колонки версии ещё нет, все pending считаются legacy. `failed`, `done`
и другие статусы не входят в этот отчёт. `pending_nonlegacy` обозначает все
прочие значения версии среди pending, а не подтверждённую пригодность для v1.
Отсутствие обязательной схемы outbox завершает команду с кодом 1 и сообщением
без деталей данных. Код 0 означает успешный аудит, а не разрешение отправки.

## Состав отчёта

Каждая строка содержит:

- `id`, `op_type`, `user_id`, сохранённый статус `pending`, эффективную версию 0
  и `protocol_source`: `column_missing`, `null` либо `zero`.
- `user`: существование пользователя, активность и `validity`.
  `valid` требует существующего активного пользователя; `null`, `missing`,
  `inactive`, `unverifiable` различаются явно.
- `entity_references`: ID заметок/файлов, источники ссылок, существование,
  ID/валидность владельца, совпадение с пользователем операции, tombstone при
  наличии колонки. Для файлов также показывается `parent_note_id`.
- `mappings`: исторические note mappings и кандидаты v1 для каждой ссылки.
  Старые mappings всегда `unscoped`: они не доказывают user/client/remote.
  Для v1 отдельно считаются точные совпадения всех трёх компонентов scope
  из самой операции. Другой user, client или remote не может быть выбран
  автоматически. URL remote и значения ключей scope не выводятся.
- `compatibility`: всегда `v1=incompatible_legacy_protocol`; отдельно состояние
  блоков из очереди (`valid`, `normalizable`, `unsupported`, `requires_context`
  или `not_present`). Используется чистый `normalize_blocks` из текущего
  block-контракта, без импорта startup/session. Нормализация только сравнивается
  в памяти. `requires_context` означает patch блока в commit, который нельзя
  проверить без исходного блока. Это не полная проверка replay или payload v1.
- `decision=quarantined_legacy`,
  `quarantine_reason=legacy_protocol_requires_manual_migration`,
  `automatic_migration_allowed=false` и дополнительные коды `reasons`.

Ссылки извлекаются из `outbox.note_id`, известных `entity_type/entity_id`,
`localNoteId`, полей note/from/to/file, `note`, `patch`, `snapshot`,
`linksFrom`, `linksTo`, списка файлов и действий `draft`. Из блоков извлекаются
локальные ссылки `/files/<id>/...`; из найденных файлов — родительская заметка.
ID блоков не считаются ID заметок. Ссылки объединяются внутри операции по паре
тип/ID; все известные источники сохраняются. Произвольные поля расширений не
интерпретируются как новые типы сущностей.

`exists` относится к записи SQLite. Аудит не открывает файлы вложений, не
проверяет их пути/содержимое и не обращается к удалённым сущностям.
Отсутствующая локальная заметка для delete также требует отдельного доказательства
владельца и remote: историческое удаление не разрешает автоматически доверять ID.
Отсутствующая таблица/колонка для проверки обозначается как `unverifiable` или
`unavailable`, без попытки миграции схемы. Наличие точного scoped mapping — только
локальное свидетельство; `remote_verified=false` остаётся во всех случаях.

Содержимое заметок, блоков, тегов, payload, токены, пароли, email, пути вложений,
имена файлов, remote URL, `last_error`, wire/result JSON и сообщения исключений
не выводятся. Разрешены только идентификаторы, фиксированные коды, булевы значения
и счётчики. Неизвестный op type выводится как `unknown`; некорректные ID
редактируются/отклоняются. Сообщения ошибок валидатора с исходным содержимым
не сериализуются. Отчёт предназначен для локального административного разбора:
он всё же содержит запрошенные user/entity IDs.

## Результат проверки рабочей БД 2026-09-24

Проверен `/Users/vjachikslavny/OVC/src/ovc.db` через `mode=ro`:

- Pending legacy: **187**; quarantined: **187**; разрешено автоматически: **0**.
- `create_note`: **52**; `update_note`: **98**; `upload_file`: **36**; `commit`: **1**.
- Колонка `protocol_version` отсутствует у всех 187 операций.
- Пользователь операции: **184** valid, **2** missing, **1** null.
- **79** операций с отсутствующей заметкой; **41** с отсутствующим файлом.
- Ссылки на заметки: **192** вхождения, **56** различных ID;
  **113** существующих записей, **79** отсутствующих.
- Ссылки на файлы: **166** вхождений, **40** различных ID;
  **107** существующих записей, **59** отсутствующих.
- Владельцы всех существующих ссылочных сущностей валидны; это не устраняет
  другие причины карантина.
- Для **192** ссылок на заметки legacy mapping отсутствует; существующие в БД
  mappings не относятся к этим ссылкам. Таблица scoped `sync_entity_map` отсутствует.
- Блоки из очереди: **150** операций `valid`, **37** `not_present`.
- `client_id` и `remote_key` отсутствуют у **187** операций;
  `base_revision` отсутствует у **99** update/commit-операций.

`summary.by_reason` считает операции с данным кодом один раз: причины могут
пересекаться, их нельзя суммировать как независимые группы. `references.*`
считает ссылки, объединённые внутри каждой операции; один ID может встречаться
в нескольких операциях. Поэтому 41 операция с отсутствующим файлом содержит
59 отсутствующих файловых ссылок. Сводка отражает конкретный снимок БД.

До/после полного аудита совпали SHA-256, размер и mtime файла БД. WAL/SHM рядом
с этой БД отсутствовали до и после проверки. Рабочие данные не изменялись.

## Условия отдельной ручной миграции

Наличие локальной сущности или валидного блока само по себе не разрешает миграцию.
До будущей записи/отправки необходим отдельный проверенный план:

1. Зафиксировать и проверить recovery point и явный список операций.
2. Доказать владельца каждой операции, сущности и зависимости, включая удалённые
   локальные сущности; не угадывать пользователя по email или текущему входу.
3. Подтвердить user/client/remote scope, server identity и mappings на выбранном
   remote. Глобальный `sync_note_map` не является таким доказательством.
4. Проверить реальное удалённое состояние и base revision, зависимости файлов,
   SHA-256 upload, tags/outgoing links и возможность пересобрать note aggregate.
   Старый commit требует отдельного разбора действий и порядка.
5. Отдельно согласовать преобразование с новым v1 envelope, устойчивым op_id,
   receipt/replay и проверкой результата. Сохранить связь с исходными legacy
   записями и recovery point; простая смена `protocol_version=0` на `1` недопустима.

Эта задача не выполняет ни один шаг записи/миграции/отправки. Исходные 187
операций остаются pending в БД и quarantined по контракту v1.
