# Локальная резервная копия и проверка восстановления

Команды из корня OVC:

```bash
./scripts/backup_local_data.sh
./scripts/verify_backup_restore.sh data/backups/<каталог-из-вывода>
.venv/bin/python -B scripts/audit_local_data.py
```

Нужна установленная `.venv`; другой интерпретатор можно указать через `OVC_PYTHON`.
Перед копированием остановите процессы, записывающие базу или вложения. Скрипт использует
SQLite backup API (включая зафиксированные данные WAL), а не простое копирование открытого DB-файла.
Изменение БД/файлов во время копирования вызывает ошибку. Скрипт не останавливает приложение сам.

Состав копии:

- `database.sqlite3`: полный снимок SQLite, включая старые и sync-таблицы;
- `storage/0`, `storage/1`, …: фактическое хранилище и внешние пути из `files.path_*`;
- оригиналы, превью, страницы PDF, waveform, конвертированные документы и прочие производные;
- `manifest.json`: исходные абсолютные пути, соответствие каталогов, счётчики, SHA-256;
- `VERIFIED.json`: появляется только после успешной проверки временного восстановления.

Поиск хранилища повторяет приложение: `OVC_UPLOAD_ROOT`, затем существующий
`~/data/uploads`, затем `OVC/data/uploads`. База определяется из эффективного `DATABASE_URL`.
Команда работает только с файловой SQLite. Она не делает дамп удалённого PostgreSQL/Supabase.

`.env`, ключи, настройки компьютера, venv и код не копируются. Файлы с именами `.env*`,
расширениями `.key`/`.pem` и симлинки внутри хранилища требуют отдельного разбора:
скрипт завершится ошибкой, а не пропустит их незаметно. **База сама содержит приватные данные,
хеши паролей и сессий**: каталог закрыт правами доступа, но не зашифрован. Не публикуйте архив.

Проверка копирует снимок во временный каталог, проверяет SHA-256, `quick_check`, счётчики
всех таблиц (включая integrity_archive и sync v1), Alembic revision и существование путей файлов.
Старые манифесты с шестью счётчиками остаются читаемыми. Пути меняются
только в временной БД. Рабочая база и оригинальные вложения не изменяются. Изменившиеся после
копирования счётчики рабочей базы выводятся отдельно. Для старой схемы FK-нарушения показываются
как предупреждения и не исправляются. Для базы, объявляющей текущий head, любое FK-нарушение
делает backup/verify неуспешным. Revision и число нарушений должны совпадать с манифестом.
После проверки временная копия удаляется.
Повторная проверка сначала снимает прежнюю отметку VERIFIED: повреждённый снимок не останется
помеченным как успешно проверенный. Пути манифеста не могут выходить из каталога копии.

## Ручное восстановление

1. Остановите сервер, desktop и sync-процессы. Сохраните отдельную копию текущего состояния.
2. Успешно выполните `verify_backup_restore.sh` для нужного снимка.
3. Разверните `database.sqlite3` **в новый каталог**, задайте для пробного запуска отдельный
   `DATABASE_URL`. Сначала не подменяйте рабочую базу.
4. Разверните каждую запись `mappings` из манифеста. На прежнем компьютере исходные пути
   можно восстановить буквально; на другом — в новые каталоги с сохранением структуры.
   Для другого пути обновите все `files.path_*` **в восстановленной БД**, по точному
   соответствию `source → backup` из манифеста. Одного `OVC_UPLOAD_ROOT` недостаточно:
   старые абсолютные пути находятся в самой БД. Логику преобразования показывает `mapped_path()`
   в `scripts/local_data.py`.
5. На восстановленной копии проверьте `quick_check`, аудит и открытие вложений. Только затем
   переключите `DATABASE_URL`/хранилище. Не переносите старые `-wal`/`-shm` поверх нового снимка.

Не запускайте разрушительные миграции до появления проверенной точки восстановления.
Незавершённый каталог без успешной проверки не считается такой точкой.

## Контролируемое присвоение бесхозных записей

Обычные API больше не присваивают записи с `user_id=NULL`. Для администратора есть отдельный
`scripts/repair_orphan_ownership.py`: сначала подготовьте JSON-план с `user_id`, `note_ids`,
`file_ids` и просмотрите результат dry-run. Скрипт не выбирает владельца самостоятельно.

```bash
.venv/bin/python -B scripts/repair_orphan_ownership.py /path/to/reviewed-plan.json
# Только после проверки плана и свежей проверенной копии:
.venv/bin/python -B scripts/repair_orphan_ownership.py /path/to/reviewed-plan.json \
  --apply --backup data/backups/<проверенная-копия>
```

Он отказывается менять существующего владельца, назначать чужие вложения/связи и применять
план без проверенной копии той же базы. Это не универсальный ремонт FK и не средство связывания
Supabase-аккаунтов. В рамках этапов 0–2 **никакой план ремонта к рабочей базе не применялся**.
